처음 구상을 한 건 학부연구생 2학년 때였다. 그때는 뭣도 몰랐을 때라 주식 가격을 예측하는 모델을 만들면 가능하지 않을까 했는데… 지금 와서 생각해보면 무식해서 가능한 생각이었다. 그래서 약 2년간 개인 주식 뷰어 웹앱만 구동을 했었는데, 최근 들어 단순 가격 예측이 아닌 오픈소스 LLM, 프론티어 모델들을 사용해서 주식 애널리스트 역할을 하는 모델을 만든 사례가 많이 나오고 있다. 그렇담 나라고 못할 게 뭐가 있지? 바로 계획부터 짜기 시작했다.

## 1. 프로젝트 설계

### 1.1 참고 논문

우선 관련 논문을 찾았다.

> Xiao et al., *TradingAgents: Multi-Agents LLM Financial Trading Framework* (arXiv:2412.20138)

<div class="post-embed" data-slug="paper-001"></div>

해당 논문에서는 한 명의 트레이더가 독단적으로 투자 결정을 내리는 것이 아닌 `분석가(Analyst)`, `리서처(Researcher)`, `리스크 매니저(Risk Manager)`, `펀드매니저(Fund Manager)`를 두어 실제 투자 기관의 의사결정 프로세스를 LLM 에이전트 간의 자연어 대화 및 토론(Agentic Debate) 알고리즘으로 이식했다. 본 프로젝트는 해당 논문에서 제공하는 프레임워크를 기반으로 하되, 국내 주식시장 KOSPI에 맞게 뜯어 고칠 예정이다.

### 1.2 프레임워크 구조

논문의 프레임워크는 크게 다섯 단계로 움직인다.

**① 분석가 팀 (Analyst Team)**
네 명의 분석가가 각자 다른 관점에서 종목을 본다.
- 펀더멘털 분석가: 재무제표, 실적, 밸류에이션
- 감성 분석가: 소셜 미디어와 시장 참여자의 심리
- 뉴스 분석가: 기업·거시경제 뉴스와 그 영향
- 기술적 분석가: 가격과 거래량 기반 지표

각 분석가는 자기 영역의 보고서를 쓰고, 이 보고서가 다음 단계의 입력이 된다.

**② 리서처 팀 (Researcher Team)**
강세론자(Bull)와 약세론자(Bear)가 분석가 보고서를 두고 여러 라운드에 걸쳐 토론한다. 강세론자는 매수 근거를, 약세론자는 리스크와 반대 근거를 제시하면서 서로의 주장을 반박한다. 한쪽 관점에 치우친 판단을 막기 위한 장치다.

**③ 트레이더 (Trader)**
분석가 보고서와 토론 결과를 종합해 매수·매도·보유 여부와 규모를 결정한다.

**④ 리스크 관리 팀 (Risk Management Team)**
공격적·중립적·보수적 관점의 리스크 담당자들이 트레이더의 계획을 다시 검토한다. 포트폴리오 전체의 노출, 변동성, 유동성 측면에서 계획이 적절한지 따진다.

**⑤ 펀드매니저 (Fund Manager)**
리스크 검토 결과를 보고 최종 승인하고, 실행한다.

에이전트끼리 주고받는 정보도 전부 자연어 대화로 처리하지 않는다. 분석 결과는 구조화된 보고서로 전달하고, 토론처럼 의견을 주고받아야 하는 단계에서만 자연어 대화를 쓴다. 대화가 길어질수록 초반 정보가 흐려지는 문제를 줄이기 위해서다. 또 데이터를 모으고 정리하는 단순 작업에는 가볍고 빠른 모델을, 토론과 판단처럼 추론이 필요한 단계에는 성능이 높은 모델을 쓰는 식으로 역할에 따라 모델을 나눠 배치했다.

### 1.3 이 구조를 고른 이유

가장 큰 이유는 **판단 과정이 전부 기록으로 남는다**는 점이다.

2학년 때 생각했던 가격 예측 모델은 "내일 오른다" 또는 "내린다"라는 결과만 준다. 맞든 틀리든 왜 그렇게 판단했는지는 알 수 없다. 반면 이 구조는 어떤 분석가가 어떤 근거를 냈고, 누가 반대했고, 리스크 검토에서 무엇이 걸렸는지가 모두 텍스트로 남는다. 판단이 틀렸을 때 어느 단계에서 틀렸는지 추적할 수 있고, 그 기록 자체가 다음 개선의 재료가 된다.

두 번째 이유는 **역할 분리**다. 하나의 거대한 프롬프트에 모든 판단을 맡기면 무엇이 잘 되고 무엇이 안 되는지 구분하기 어렵다. 역할이 나뉘어 있으면 뉴스 분석만 개선하거나, 리스크 검토 기준만 바꾸는 식으로 부분 단위의 실험이 가능하다.

### 1.4 논문을 그대로 쓸 수 없는 이유

다만 논문의 프레임워크를 그대로 가져오기에는 걸리는 점들이 있다.

**첫째, 미국 시장 기준이다.** 데이터 소스, 뉴스, 시장 구조가 모두 미국 주식을 전제로 한다. 국내 시장에는 국내 데이터 소스와 국내 시장 특성을 반영해야 한다.

**둘째, LLM 호출 비용이 크다.** 종목 하나를 판단할 때마다 분석가 네 명, 여러 라운드의 토론, 리스크 검토까지 수십 번의 LLM 호출이 일어난다. 유료 API로 매일 여러 종목을 돌리면 비용이 빠르게 불어난다. 이 프로젝트는 비용을 최소화하는 것이 전제라서, 이 부분을 어떻게 줄일지가 핵심 과제다.

**셋째, 검증 기간이 짧다.** 논문의 백테스트는 수개월 수준의 기간과 소수 종목으로 이뤄졌다. 실제로 돈을 넣으려면 더 긴 기간, 다양한 시장 국면에서 검증이 필요하다.

국내 시장에 맞게 고쳐야 할 부분은 다음과 같이 정리했다.

| 항목 | 논문 (미국) | 본 프로젝트 (KOSPI) |
|---|---|---|
| 기업 정보 | SEC 공시, 재무 API | DART 전자공시 |
| 시세·주문 | 미국 증권사·데이터 API | 한국투자증권 Open API |
| 전문가 의견 | 애널리스트 리포트 등 | 네이버 금융 리서치 (국내 증권사 리포트) |
| 뉴스 | 영문 뉴스 | 국내 경제 뉴스 (한국어) |
| 추가 신호 | - | 외국인·기관 투자자별 순매수 (수급) |
| 거래 제도 | 가격제한폭 없음 | 가격제한폭 ±30%, 09:00~15:30 정규장 |

특히 **수급**은 국내 시장에서 비중을 크게 둬야 하는 신호다. 외국인과 기관의 순매수 흐름이 주가 방향에 영향을 주는 경우가 많고, 이 데이터는 매일 장 마감 후 공개된다. 논문의 분석가 구성에는 수급 전담 역할이 없기 때문에 추가하거나 기존 역할에 포함시켜야 한다.

## 2. 모델 구성

### 2.1 선정 기준

어떤 알고리즘, 프레임워크를 쓸지는 정했으니 이제 프레임워크를 구성할 모델을 선정해야 한다. 우선 다음과 같은 기준을 세우고 모델을 탐색했다.

1. 돈이 많이 들지 않을 것
2. 온디바이스 구동을 위해 가볍고 성능이 좋을 것
3. 한국어에 적합한 모델일 것

세 번째 조건이 특히 중요하다. 이 프로젝트에서 모델이 읽어야 하는 공시, 뉴스, 증권사 리포트는 전부 한국어다. 게다가 금융 문서는 "컨센서스 상회", "목표주가 하향", "비중확대" 같은 도메인 표현이 많다. 영어 중심 모델은 일반적인 한국어 대화는 곧잘 해도 이런 문서에서 뉘앙스를 놓치는 경우가 있다.

### 2.2 구동 환경

평소에 데스크탑보다 맥북을 주로 사용하기 때문에 사양은 맥북을 기준으로 잡았다.

> MacBook Pro 14, Apple M2 MAX, 32GB

애플 실리콘은 CPU와 GPU가 메모리를 공유하는 통합 메모리 구조라서, 32GB 안에서 모델을 올릴 수 있다. 4-bit 양자화 기준으로 대략적인 메모리 사용량을 계산해보면 다음과 같다.

| 모델 크기 | 4-bit 양자화 시 가중치 | 비고 |
|---|---|---|
| 8B | 약 5GB | 컨텍스트를 길게 잡아도 여유 있음 |
| 14B | 약 9GB | 무난하게 구동 가능 |
| 32B | 약 18~20GB | 구동은 가능하지만 컨텍스트와 다른 작업 여유가 줄어듦 |

가중치 외에도 입력 문서를 담는 컨텍스트(KV 캐시)와 운영체제, 다른 프로그램이 메모리를 나눠 써야 한다. 증권사 리포트처럼 긴 문서를 넣으면 컨텍스트 메모리가 꽤 커지기 때문에, 상시로 쓸 모델은 8B급이 현실적이고 30B급은 필요할 때만 올리는 방식이 맞다고 판단했다.

### 2.3 후보 모델 비교

위 기준으로 후보를 추렸다.

| 모델 | 크기 | 한국어 | 라이선스 | 평가 |
|---|---|---|---|---|
| Kanana 1.5 (카카오) | 8B | 한국어 특화 | Apache 2.0 | 세 가지 조건을 모두 충족 |
| EXAONE (LG) | 7.8B 등 | 우수 | 비상업(NC) | 성능은 좋으나 상업적 확장 불가 |
| Qwen3 (알리바바) | 8B | 보통 | Apache 2.0 | 학습·추론 도구 지원이 가장 넓음. 한국어 표현은 국산 모델 대비 아쉬움 |
| HyperCLOVA X SEED (네이버) | 소형 | 우수 | 조건부 상업 허용 | 가볍지만 긴 문서 분석에는 체급이 작음 |
| Kanana-2 (카카오) | 32B MoE (활성 3B) | 한국어 특화 | 조건부 상업 허용 | 추론은 맥북에서 가능. 파인튜닝은 부담 |

라이선스를 따진 이유는 확장 가능성 때문이다. 처음에는 개인용으로 만들지만, 결과가 좋으면 앱이나 서비스로 발전시킬 수도 있다. 그때 비상업 라이선스 모델을 쓰고 있었다면 모델을 교체하고 학습을 처음부터 다시 해야 한다. 처음부터 라이선스 제약이 적은 모델로 가는 편이 낫다고 봤다.

Kanana-2는 MoE(Mixture of Experts) 구조라 전체 파라미터는 32B지만 한 번에 활성화되는 파라미터는 3B 수준이다. 추론 속도는 가볍지만, 메모리에는 전체 가중치를 올려야 하기 때문에 메모리 요구량은 32B 모델과 같다. 추론용으로는 매력적이지만, 학습까지 고려하면 부담이 크다.

### 2.4 최종 선택과 역할 분담

결론은 **Kanana 계열**이다. 한국어 특화와 자유로운 라이선스를 동시에 만족하는 조합은 현재 이것이 유일했다.

다만 로컬 8B 모델 하나로 모든 역할을 처리하기는 어렵다고 봤다. 논문에서 역할에 따라 모델을 나눠 쓴 것처럼, 이 프로젝트도 작업 성격에 따라 모델을 나누기로 했다.

| 작업 | 특징 | 사용 모델 |
|---|---|---|
| 뉴스·리포트 요약, 분류 | 호출 수가 많고 반복적 | 로컬 Kanana 1.5 8B |
| 종합 판단, 토론 | 호출 수는 적지만 추론이 중요 | 로컬 모델 + Gemini 무료 티어 보조 |
| 리포트 문체 생성 | 특정 양식을 따라야 함 | Kanana 1.5 8B 파인튜닝 |

반복 작업은 로컬 모델이 맡아 비용을 0으로 만들고, 추론이 중요한 소수의 작업에만 프론티어 모델의 무료 사용량을 쓰는 구조다. 무료 사용량이 막히더라도 로컬 모델로 계속 돌아가도록 설계해야 한다.

## 3. 데이터 구성

### 3.1 필요한 데이터

프레임워크의 각 역할이 판단하려면 그에 맞는 데이터가 필요하다. 국내 시장 기준으로 필요한 데이터와 출처를 정리했다.

| 데이터 | 출처 | 갱신 주기 | 사용 역할 |
|---|---|---|---|
| 일봉·분봉 시세 | 한국투자증권 Open API | 장중·장후 | 기술적 분석, 리스크 관리 |
| 투자자별 순매수 | pykrx | 장후 | 수급 분석 |
| 재무제표 | DART OpenAPI | 분기 | 펀더멘털 분석 |
| 공시 | DART OpenAPI | 수시 | 뉴스 분석, 리스크 관리 |
| 경제 뉴스 | 네이버 뉴스 검색 API, 언론사 RSS | 수시 | 뉴스·감성 분석 |
| 증권사 리포트 | 네이버 금융 리서치 | 매일 | 펀더멘털 분석, 리포트 문체 학습 |
| 계좌·체결 | 한국투자증권 Open API | 장중 | 리스크 관리, 현황 보고 |

전부 무료로 접근할 수 있는 소스다. 유료 데이터 벤더를 쓰지 않는다는 원칙은 모델 선정과 같은 이유다.

### 3.2 공시와 뉴스의 관계

국내 시장에서는 **공시가 원본이고, 뉴스는 대부분 공시를 받아쓴 것**이라는 점을 설계에 반영하기로 했다. 실적 발표, 수주 계약, 유상증자, 자사주 매입 같은 굵직한 사건은 DART 공시가 먼저 나오고, 뉴스는 이를 요약하거나 해석한다. 그래서 공시를 사건의 기준으로 삼고, 뉴스는 공시에 없는 정보(업황, 정책, 시장 반응, 루머)를 보강하는 용도로 쓴다. 같은 사건을 다룬 기사 수십 개를 LLM이 각각 읽는 낭비도 줄일 수 있다.

### 3.3 증권사 리포트의 두 가지 용도

증권사 리포트는 이 프로젝트에서 두 번 쓰인다.

첫째는 **분석 입력**이다. 투자의견과 목표주가가 바뀌었다는 사실 자체가 시장에 영향을 주는 정보다. 여러 증권사가 같은 방향으로 목표주가를 바꾼다면 더 강한 신호가 된다.

둘째는 **문체 학습 데이터**다. 최종적으로 이 시스템이 만들어내는 결과물은 애널리스트 리포트 형식의 분석 보고서다. 결론을 먼저 쓰고, 근거를 뒤에 붙이고, 수치를 표로 정리하는 증권사 리포트 특유의 양식을 모델이 익히려면 실제 리포트로 학습해야 한다. 다만 리포트의 저작권은 각 증권사에 있기 때문에, 학습 데이터와 학습된 모델은 개인 용도로만 사용하고 외부에 공개하지 않는다.

### 3.4 미래 데이터 누수 문제

데이터를 모으면서 가장 조심해야 할 부분은 **미래 정보가 과거 판단에 섞이는 문제**다.

예를 들어 3분기 실적은 9월 30일에 분기가 끝나지만, 실제 공시는 11월 중순에 나온다. 과거 데이터로 백테스트를 할 때 이 실적을 9월 30일부터 알고 있었던 것처럼 처리하면, 당시에는 알 수 없었던 정보로 판단한 셈이 된다. 백테스트 성과가 실제보다 좋게 나오고, 실전에서 그 성과가 재현되지 않는다.

그래서 모든 데이터에 **실제로 사용 가능해진 시점**을 함께 저장하기로 했다. 재무제표는 공시 접수일, 뉴스는 발행 시각을 기준으로 삼고, 장 마감 이후 나온 정보는 다음 거래일부터 사용한다. 상장폐지된 종목도 삭제하지 않고 남겨둔다. 살아남은 종목만으로 백테스트하면 역시 결과가 부풀려지기 때문이다.

## 4. 남은 문제와 다음 계획

프레임워크, 모델, 데이터까지 정하고 나니 풀어야 할 문제들이 보이기 시작했다.

### 4.1 토론 구조의 호출 수

로컬 모델을 쓰면 비용은 0이 되지만 시간은 그대로다. 종목 하나에 수십 번의 호출이 필요한 토론 구조를 매일 수십 종목에 돌리면, 8B 모델이라도 장 마감 후 몇 시간이 걸릴 수 있다. 모든 판단을 에이전트 토론으로 처리할지, 계산으로 끝낼 수 있는 부분은 코드로 처리하고 LLM은 해석에만 쓸지 다시 생각해봐야 한다.

### 4.2 학습 환경

Kanana 1.5 8B를 리포트 양식에 맞게 파인튜닝하려면 LoRA 계열 학습이 필요하다. 문제는 현재 널리 쓰이는 학습 도구 대부분이 NVIDIA GPU(CUDA)를 기준으로 만들어져 있다는 점이다. 맥북에서도 학습 자체는 가능하지만, 도구 지원과 속도에서 제약이 크다.

### 4.3 상시 구동

자동매매까지 연결하려면 장중 내내 켜져 있으면서 손절 조건을 감시하는 컴퓨터가 필요하다. 맥북은 들고 다니는 기기라 절전 모드, 이동, 재부팅이 수시로 일어난다. 실제 돈이 걸린 시스템을 맡기기에는 적합하지 않다.

### 4.4 리스크 관리를 LLM에게 맡겨도 되는가

가장 고민되는 부분이다. 논문에서는 리스크 관리 팀과 펀드매니저도 LLM 에이전트다. 하지만 LLM은 같은 입력에도 다른 답을 낼 수 있고, 입력이 이상하면 이상한 결론을 그럴듯하게 설명하기도 한다. 분석과 해석은 LLM에게 맡기더라도, 실제 주문을 막고 허용하는 최종 관문까지 LLM에게 맡기는 것이 맞는지는 확신이 서지 않는다.

### 4.5 다음 편에서

4.2와 4.3은 하드웨어 문제라 답이 비교적 명확했다. 학습과 상시 구동을 모두 해결할 수 있는 장비로 운영 환경을 옮기는 것이다. 4.1과 4.4는 설계 자체를 다시 봐야 하는 문제였고, 결과적으로 프레임워크 구조를 꽤 많이 바꾸게 됐다.

2편에서는 운영 환경을 어떻게 정했는지, 그리고 논문의 에이전트 토론 구조가 실제로 어떤 모습으로 바뀌었는지를 정리할 예정이다.
