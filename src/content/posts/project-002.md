1편 마지막에서 네 가지 문제를 남겼다.

1. 토론 구조는 LLM 호출 수가 너무 많다
2. 맥북에서는 파인튜닝 환경이 제한적이다
3. 자동매매를 하려면 상시로 켜져 있는 컴퓨터가 필요하다
4. 리스크 관리를 LLM에게 맡겨도 되는지 확신이 없다

2번과 3번은 장비 문제였고, 1번과 4번은 설계 자체의 문제였다. 이번 편에서는 이 네 가지에 대한 답을 정리하면서, 최종적으로 확정한 시스템 구조를 모듈 단위로 설명한다.

## 1. 운영 환경: 데스크탑으로 옮기다

### 1.1 선택지

상시 구동과 학습을 모두 해결할 수 있는 선택지는 세 가지였다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 클라우드 무료 VM | 비용 0원, 상시 가동 | 무료 사양이 예고 없이 줄어들 수 있고, 사용률이 낮으면 인스턴스가 회수될 수 있음. GPU 없음 |
| 맥북 | 추가 비용 없음, 통합 메모리 32GB | 이동·절전이 잦아 상시 구동 불가, CUDA 미지원 |
| 로컬 데스크탑 | 상시 구동, CUDA 학습 가능, 정책 리스크 없음 | 전기료, 정전·업데이트 재부팅 대응 필요 |

클라우드 무료 VM은 비용 면에서 가장 이상적이지만, 무료 티어 정책은 제공사 사정에 따라 바뀐다. 실제 돈이 걸린 매매 시스템을 언제 사양이 바뀔지 모르는 환경에 올려두기는 어려웠다. 또 이 시스템은 대부분의 시간 동안 부하가 가벼워서, 사용률이 낮은 인스턴스를 회수하는 정책에 걸릴 가능성도 있었다.

결론은 **로컬 데스크탑**이다.

> Desktop, NVIDIA RTX 4070 SUPER (12GB VRAM)

### 1.2 맥북과 데스크탑의 역할 분담

데스크탑이 모든 면에서 맥북보다 나은 것은 아니다. 맥북은 통합 메모리 32GB라서 추론만 놓고 보면 12GB VRAM보다 큰 모델을 올릴 수 있다. 그래서 역할을 나눴다.

| 기기 | 역할 |
|---|---|
| 데스크탑 (4070 SUPER) | 운영 서버: 데이터 수집, 분석, 리포트 생성, 자동매매, 모델 학습 |
| 맥북 (M2 Max 32GB) | 개발 환경, 대형 모델(32B급) 추론 비교 실험 |

### 1.3 12GB VRAM 안에서 살아남기

12GB는 넉넉한 용량이 아니다. Kanana 1.5 8B를 4-bit로 양자화해 추론용으로 올리면 약 5GB, QLoRA로 학습하면 설정에 따라 9~11GB를 쓴다. **학습과 추론을 동시에 올릴 수 없다**는 뜻이다.

그래서 GPU 사용 시간표를 정했다.

| 시간 (거래일) | GPU 용도 | 비고 |
|---|---|---|
| 16:00 ~ 16:40 | 분석 해석, 리포트 생성 | 최우선. 학습 금지 |
| 17:00 ~ 익일 06:30 | 리포트 정밀 파싱 → 모델 학습 | 30분마다 체크포인트, 06:30 강제 종료 |
| 주말·휴장일 | 학습 | 월요일 06:30 강제 종료 |

GPU를 쓰는 모든 코드는 락을 먼저 잡도록 했다. 만약 학습이 길어져 리포트 생성 시각에 GPU를 쓸 수 없으면, 리포트는 기다리지 않고 바로 Gemini 무료 티어로 넘어간다. 학습 때문에 매일의 리포트가 늦어지는 일은 없어야 한다.

Kanana-2(32B MoE)는 4-bit로도 12GB를 넘기 때문에 학습 대상에서 제외했다. 추론 품질 비교는 맥북에서 따로 진행한다.

### 1.4 서버로서의 데스크탑

집에 있는 데스크탑을 서버로 쓰려면 몇 가지를 먼저 설정해야 한다.

- 절전 모드와 디스크 절전을 끈다
- BIOS에서 정전 후 전원이 돌아오면 자동으로 부팅되도록 설정한다
- OS 자동 업데이트로 인한 재부팅을 막고, 업데이트는 주말에 수동으로 적용한다
- 부팅되면 추론 서버, 스케줄러, 텔레그램 봇이 순서대로 자동 시작되게 한다
- 5분마다 외부 모니터링 서비스로 신호를 보내고, 신호가 끊기면 휴대폰으로 알림이 오게 한다

그래도 컴퓨터는 꺼질 수 있다. 그래서 보유 종목에는 증권사 앱의 자동감시주문(스탑로스)을 **별도로 걸어두기로** 했다. 서버가 멈춰도 손절은 증권사 쪽에서 동작하도록 이중으로 안전장치를 두는 것이다.

## 2. 구조 재설계: 에이전트 토론에서 모듈 파이프라인으로

### 2.1 왜 토론 구조를 그대로 쓰지 않았나

1편에서 정리한 TradingAgents 구조는 분석부터 최종 승인까지 모든 단계가 LLM 에이전트다. 설계를 구체화하면서 이 구조의 문제가 더 분명해졌다.

**계산할 수 있는 것까지 LLM에게 묻고 있다.** 이동평균, RSI, PER 같은 지표는 공식이 정해져 있다. 이를 LLM이 계산하거나 해석하게 하면 느리고, 가끔 틀리고, 같은 입력에도 다른 답이 나온다. 코드로 계산하면 빠르고, 항상 같고, 틀리지 않는다.

**호출 수가 종목 수에 비례해 폭증한다.** 종목마다 분석가 네 명, 토론 여러 라운드, 리스크 검토까지 하면 호출 수가 수십 번이다. 로컬 모델이라 비용은 없지만, 장 마감 후 제한된 시간 안에 수십 종목을 처리해야 한다.

**리스크 관리가 비결정적이다.** 1편 4.4절의 고민으로 돌아가면, 주문을 막아야 할 상황에서 LLM이 설득력 있는 이유를 붙여 통과시킬 가능성을 완전히 배제할 수 없다. 돈이 걸린 최종 관문은 매번 똑같이 동작해야 한다.

### 2.2 논문 역할과 새 구조의 대응

그래서 역할 구성은 유지하되, 각 역할을 **코드가 할 일과 LLM이 할 일로 다시 나눴다.**

| 논문 속 역할 | 새 구조 | 코드가 하는 일 | LLM이 하는 일 |
|---|---|---|---|
| 분석가 팀 | 뉴스 AI + 투자 분석 AI | 지표 계산, 점수화, 이벤트 분류 | 점수의 해석, 신호 충돌 설명 |
| 리서처 팀 (토론) | 투자 분석 AI 해석 층 | - | 충돌 신호 정리 (토론 구조는 추후 실험) |
| 트레이더 | 규칙 기반 전략 | 진입·청산 조건, 포지션 크기 | 없음 |
| 리스크 관리 팀 | 리스크 게이트 | 한도·비중·손실 규칙 검사 | **없음** |
| 펀드매니저 | 주문 실행기 | 주문 집행, 체결 동기화 | 없음 |
| (없음) | 리포트 AI + 장마감 보고 | 콘텐츠 선정, 숫자 채우기, 검증 | 애널리스트 양식의 글쓰기 |

가장 큰 변화는 **리스크 관리를 LLM에서 하드코딩된 규칙으로 옮긴 것**과, 논문에는 없던 **리포트 층을 추가한 것**이다. 판단 과정이 기록으로 남는다는 1편의 장점은 리포트 층이 이어받는다. 매일 장 마감 후 무엇을 근거로 어떤 판단을 했는지가 애널리스트 리포트 형식으로 남는다.

강세/약세 토론은 버리지 않았다. 장 마감 후 배치에서 종목별로 강세 논리와 약세 논리를 한 번씩 쓰게 하고, 그 결과를 점수에 제한된 범위(±10점)로만 반영하는 방식으로 추후 실험할 계획이다.

### 2.3 전체 구조

최종 구조는 공통 데이터 레이어 위에 세 개의 AI 모듈이 있고, 그 결과를 자동매매와 장마감 보고가 받아쓰는 형태다.

```
공통 데이터 레이어 (시세 · 수급 · 공시 · 뉴스 · 증권사 리포트)
        │
        ├──▶ 뉴스 AI ──▶ 투자 분석 AI ──▶ 리포트 AI
        │        │              │               │
        │        └──────▶ 자동매매 ◀─────┘        │
        │                    │                  │
        └────────────────────┴──▶ 장마감 보고 ◀──┘ ──▶ 텔레그램
```

세 AI 모듈은 **병렬로 개발**한다. 모듈 사이에서 주고받는 데이터 형식(JSON 스키마)을 먼저 고정해두면, 다른 모듈이 완성되지 않아도 가짜 입력으로 각자 개발하고 테스트할 수 있다.

## 3. 설계 원칙

구조를 짜면서 모든 모듈에 공통으로 적용할 원칙을 정했다. 코드가 이 원칙을 어기면 기능이 동작하더라도 받아들이지 않는다.

### 3.1 LLM은 주문하지 않는다

주문은 `전략 → 리스크 게이트 → 실행기` 한 가지 경로로만 나간다. LLM의 출력은 점수, 근거, 문장으로만 쓰이고, 주문을 직접 만들거나 게이트를 통과시키는 데 관여하지 않는다. 매매 모듈은 LLM 클라이언트를 아예 불러오지 않도록 했다.

### 3.2 숫자는 코드가 쓴다

리포트를 LLM이 쓰면 가장 흔한 사고가 숫자다. "외국인이 1,240억원 순매수"를 "1,420억원"으로 쓰는 식의 오류는 문장이 그럴듯해서 발견하기도 어렵다.

그래서 모델이 숫자를 직접 쓰지 않고 **참조 슬롯**을 쓰도록 했다.

```
모델 출력: 삼성전자는 {005930.change_pct} 상승한 {005930.close}원에 마감했으며,
           외국인이 {005930.foreign_net_5d} 순매수하며 매수세를 이어갔다.
최종 결과: 삼성전자는 2.3% 상승한 84,500원에 마감했으며,
           외국인이 1,240억원 순매수하며 매수세를 이어갔다.
```

모델은 문맥과 문체만 담당하고, 실제 값과 단위 표기(억, 조, 부호)는 코드가 채운다. 입력에 없는 슬롯을 참조하면 바로 오류로 잡힌다. 학습 데이터도 같은 방식으로 만들어서, 모델이 애초에 숫자를 지어내는 법을 배우지 않게 한다.

### 3.3 미래 데이터를 쓰지 않는다

1편 3.4절에서 다룬 문제를 코드 수준의 규칙으로 만들었다. 모든 데이터 조회 함수는 `as_of`(기준일)를 받고, 그 시점에 실제로 알 수 있었던 데이터만 반환한다.

| 데이터 | 사용 가능 시점 |
|---|---|
| 재무제표 | DART 공시 접수일 (15:30 이후 접수면 다음 거래일) |
| 공시·뉴스 | 발행 시각이 15:30 이전이면 당일, 이후면 다음 거래일 |
| 투자자별 수급 | 장 마감 후 확정. 당일 장중 판단에는 사용 금지 |
| 증권사 리포트 | 목록에 발행 시각이 없으므로 보수적으로 다음 거래일 |

상장폐지 종목도 삭제하지 않는다. 백테스트 루프에서 기준일보다 늦게 공개된 데이터가 한 건이라도 조회되면 테스트가 실패하도록 감시 장치를 달았다.

### 3.4 장중에는 LLM을 쓰지 않는다

실행을 두 계층으로 나눴다.

| 계층 | 실행 시점 | 하는 일 | LLM |
|---|---|---|---|
| 배치 계층 | 장전·장후 | 수집, 분석, 리포트, 다음 날 주문 계획 | 사용 |
| 실시간 계층 | 장중 09:00~15:30 | 가격 감시, 손절·익절, 계획된 주문 집행 | 사용 안 함 |

장중에 LLM 응답을 기다리다 손절 타이밍을 놓치는 일이 없도록, 장중에는 전날 밤 확정된 주문 계획과 가격 데이터만으로 결정론적으로 움직인다.

## 4. 모듈별 설계

### 4.1 공통 데이터 레이어

모든 모듈이 같은 데이터를 쓰기 때문에 수집과 저장은 한 곳에서 처리한다. API 응답 원본은 Parquet 파일로 날짜별로 보관하고, 정제된 데이터와 모듈의 산출물은 SQLite 하나에 저장한다. 모든 데이터는 `종목코드 + 날짜`를 키로 연결된다.

과거 데이터는 2015년부터 KOSPI 전 종목(상장폐지 포함)의 일봉, 수급, 재무, 공시를 백필한다. 매일 수집이 끝나면 품질 검사를 돌려서, 누락이나 이상치가 있는 종목은 그날 분석에서 제외하고 알림을 보낸다.

### 4.2 뉴스 AI

뉴스 AI의 목표는 쏟아지는 기사를 **"기사"가 아니라 "사건" 단위**로 정리하는 것이다. 처리는 다음 순서로 진행된다.

1. **수집**: DART 공시, 네이버 뉴스 검색 API, 언론사 RSS
2. **정제**: 광고성 기사, 등락률만 나열한 자동 생성 기사 제거
3. **중복 제거**: 제목 임베딩 유사도로 같은 사건을 다룬 기사들을 하나로 묶음. 묶인 기사 수는 그 자체로 중요도 신호가 된다
4. **종목 매핑**: 약칭, 영문명, 자회사명까지 담은 사전으로 매칭. "현대"처럼 모호한 경우만 LLM이 판정
5. **분류**: 이벤트 유형, 감성, 확실성, 중요도 판정
6. **집계**: 종목별 최근 1·5·20일 이벤트 요약

1편에서 정한 대로 공시가 원본이다. DART 공시는 공시 유형 코드로 이미 분류되어 있어서, LLM을 거치지 않고 매핑 테이블로 바로 이벤트가 된다.

이벤트 분류 체계는 처음부터 고정했다. 나중에 바꾸면 쌓아둔 라벨이 전부 쓸모없어지기 때문이다.

| 대분류 | 예시 | 기본 방향 |
|---|---|---|
| 실적 | 잠정실적, 어닝 서프라이즈/쇼크 | 컨센서스 대비 |
| 영업 | 수주·공급계약, 신제품 | 대체로 긍정 |
| 자본 | 유상증자, CB·BW 발행, 자사주 매입 | 희석은 부정, 주주환원은 긍정 |
| 지배구조 | M&A, 최대주주 변경 | 사안별 |
| 리스크 | 소송, 규제, 감사의견 | 대체로 부정 |
| 업황정책·매크로 | 산업 정책, 금리, 환율 | 섹터·시장 단위 |
| 리서치 | 목표주가·투자의견 변경 | 상향은 긍정, 하향은 부정 |

여기서 **감성은 문장의 논조가 아니라 예상 주가 영향**으로 정의했다. "대규모 투자 단행"은 논조는 긍정이지만 재무 부담이 크면 주가에는 부정일 수 있고, "적자 폭 축소"는 논조는 부정이지만 주가에는 긍정일 수 있다. 일반적인 감성 분석 모델을 그대로 쓸 수 없는 이유다.

유상증자나 전환사채 발행 같은 **희석 이벤트**는 별도 플래그를 달아, 투자 분석에서는 매수 시그널의 상한을 낮추고 자동매매에서는 신규 매수를 막는다.

분류는 처음에는 Gemini로 하되, 그 판정 결과를 전부 라벨로 쌓는다. 라벨이 수천 건 모이면 한국어 소형 인코더 모델을 학습시켜 대부분의 분류를 맡기고, 소형 모델이 확신하지 못하는 경우에만 Gemini를 부른다. 무료 사용량 한도를 지키면서 속도도 확보하는 방법이다.

분류가 맞았는지는 결국 주가로 확인한다. 월 1회 이벤트 유형별로 발생 이후 며칠간의 시장 대비 초과수익을 계산해서(이벤트 스터디), 실제로 의미 있는 유형과 그렇지 않은 유형을 가려내고 그 결과를 분석 가중치에 반영한다.

### 4.3 증권사 리포트 수집

1편 3.3절에서 증권사 리포트를 분석 입력과 학습 데이터로 쓰겠다고 했는데, 설계하면서 용도가 하나 더 늘었다. 매일의 장마감 보고에 **"오늘의 리서치"** 섹션으로도 들어간다. 수집 파이프라인 하나로 세 가지를 모두 챙기는 구조다.

| 용도 | 쓰는 방식 |
|---|---|
| 분석 입력 | 목표주가·투자의견 변경을 이벤트로 만들고, 분석 피처로 사용 |
| 장마감 보고 | 그날 주목할 리포트를 골라 1~2문장으로 요약 |
| 학습 데이터 | 리포트 문체를 학습시키기 위한 데이터셋 |

네이버 금융 리서치의 6개 카테고리(종목분석, 산업분석, 시황정보, 투자정보, 경제분석, 채권분석)를 거래일 11:30과 17:00 두 번 수집한다. 리포트는 오전 중에 순차적으로 올라오기 때문에, 장 시작 전에 수집하면 대부분 비어 있다. 요청 사이에는 간격을 두고, 이미 받은 PDF는 다시 받지 않는다.

텍스트 추출은 두 갈래로 나눴다. 장마감 요약용으로는 PDF 앞 3페이지만 빠르게 추출하고, 학습용으로는 밤 시간대에 레이아웃을 인식하는 파서로 표와 2단 편집을 살려 정밀하게 변환한다.

목표주가·투자의견 변화는 같은 증권사가 같은 종목에 대해 낸 직전 리포트와 비교해 규칙으로 계산한다. LLM을 쓰지 않는다. 같은 날 여러 증권사가 같은 방향으로 목표주가를 바꾸면 하나의 이벤트로 묶어 더 강한 신호로 처리한다.

장마감 보고에 올릴 리포트는 다음 점수로 고른다.

> 선정 점수 = 조회수 정규화(0~100) + 대형 증권사 30 + 보유·관심 종목 관련 50 + 의견·목표가 변경 20

조회수와 증권사 규모만 보면 시장 전체에서 인기 있는 리포트가 올라오지만, 여기에 보유·관심 종목 가중치를 더해 **내 포트폴리오와 관련된 리포트가 먼저 보이도록** 했다.

리포트의 저작권은 각 증권사에 있으므로, 원문과 요약은 개인 용도로만 쓰고 외부 채널로 공유하지 않는다.

### 4.4 투자 분석 AI

투자 분석 AI는 판단 재료를 만드는 모듈이고, **주문 권한은 없다.** 4개 층으로 나뉜다.

**① 피처 계산 (코드)**

| 영역 | 주요 피처 |
|---|---|
| 추세 | 20·60·120일 이동평균 배열, 이평 기울기 |
| 모멘텀 | RSI(14), 20·60일 수익률, 52주 고점 대비 위치 |
| 변동성 | ATR, 볼린저 밴드 폭 |
| 거래량 | 20일 평균 대비 거래량 배수 |
| 수급 | 외국인·기관 5·20일 누적 순매수 |
| 밸류 | PER·PBR의 섹터 내 백분위, 자기 5년 백분위 |
| 실적 | 영업이익 증가율, ROE, 부채비율 |
| 이벤트 | 뉴스 AI 이벤트 점수, 희석 이벤트 여부 |
| 리서치 | 20일 목표가 상향·하향 건수, 커버 증권사 수, 목표가 괴리율 |

리서치 피처에서는 목표가의 **수준보다 변화**를 주 신호로 쓴다. 증권사 목표가에는 낙관적인 편향이 있어서, 목표가가 현재가보다 높다는 사실만으로는 정보가 적다. 반면 목표가를 올렸다는 변화는 새로운 정보다.

**② 서브 스코어**

피처를 기술, 수급, 펀더멘털, 이벤트 네 가지 점수(0~100)로 묶는다. 이때 값을 그대로 쓰지 않고 **섹터 안에서의 백분위**로 바꾼다. 은행주의 PBR 0.5와 바이오주의 PBR 0.5는 의미가 전혀 다르기 때문이다. 장기 백분위 기준에는 기존에 구축해둔 한국 상장기업 재무 패널 데이터를 활용한다.

여기에 **시장 국면(레짐)** 판단을 더했다. KOSPI 지수의 추세와 변동성으로 상승장, 횡보장, 하락장을 나누고, 하락장에서는 개별 종목 점수가 높아도 매수 시그널을 억제한다.

**③ 결합**

처음에는 가중합(기술 30%, 수급 25%, 펀더멘털 30%, 이벤트 15%)으로 시작한다. 해석이 쉽고 디버깅이 편하다. 이후 향후 20거래일 동안 시장 대비 초과수익 상위 30%에 들었는지를 라벨로 삼아 LightGBM 모델을 학습시키고, 시간 순서대로 학습 구간을 밀어가며 검증(walk-forward)해서 가중합보다 성능이 좋을 때만 교체한다.

최종 점수는 5단계 시그널로 바뀐다.

| 최종 점수 | 시그널 |
|---|---|
| 80 이상 | 강력매수 |
| 65 ~ 80 | 매수 |
| 45 ~ 65 | 관망 |
| 30 ~ 45 | 축소 |
| 30 미만 | 매도 |

**④ LLM 해석**

LLM에게는 세 가지만 맡긴다. 점수를 보고 근거 문장 쓰기, 신호끼리 충돌할 때(예: 기술적으로는 강세인데 외국인은 계속 매도) 상황을 설명하기, 뉴스 맥락을 반영해 점수를 **±10점 범위 안에서만** 조정하기. LLM이 전부 실패해도 점수와 시그널은 정상적으로 나오도록 했다.

### 4.5 리포트 AI

리포트 AI의 원칙은 **"무엇을 쓸지는 코드가, 어떻게 쓸지는 모델이"**다.

**파이프라인**

1. **콘텐츠 선정 (코드)**: 보유 종목 중 등락률 상위, 시그널이 바뀐 종목, 중요도 높은 이벤트, 리스크 이벤트, 주목할 리서치를 규칙으로 고른다. LLM에게 무엇을 넣을지 고르게 하면 매일 비중이 들쭉날쭉해진다.
2. **섹션별 생성 (LLM)**: 리포트 전체를 한 번에 쓰지 않고 섹션마다 필요한 입력만 넣어 생성한다. 입력이 짧아지니 8B 모델로도 감당할 수 있다.
3. **검증 (코드)**: 슬롯 밖의 숫자가 있는지, 상승·하락 같은 방향어가 실제 값의 부호와 맞는지, 언급한 종목이 입력에 있는지 검사한다. 실패하면 최대 2번 다시 생성하고, 그래도 실패하면 그 섹션만 LLM 없이 템플릿 문장으로 대체한다.
4. **렌더링 (코드)**: HTML 리포트, 차트, 텔레그램 요약 메시지로 변환한다.

모델은 `로컬 파인튜닝 모델 → Gemini → 템플릿` 순서로 폴백한다. 어떤 상황에서도 리포트는 나간다.

**학습 데이터 만들기**

리포트 문체를 학습시키려면 "이런 입력을 주면 이런 리포트가 나온다"는 쌍이 필요하다. 문제는 증권사 리포트에는 출력(리포트 본문)만 있고 입력이 없다는 점이다. 그래서 **역방향으로** 만든다.

1. 리포트 본문에서 수치, 이벤트, 결론을 구조화된 형태로 추출한다
2. 본문의 숫자를 추출된 데이터의 슬롯으로 치환한다
3. (추출 데이터 → 슬롯 치환된 본문) 쌍이 학습 샘플이 된다

실제 운영에서는 추출 데이터 자리에 시스템이 계산한 데이터가 들어간다. 학습·검증·테스트 데이터는 무작위가 아니라 날짜 기준으로 나눈다.

**파인튜닝**

Kanana 1.5 8B Instruct를 데스크탑에서 QLoRA로 학습한다. 12GB VRAM에 맞춰 4-bit 양자화, LoRA rank 16, 시퀀스 길이 2,048, gradient checkpointing으로 설정했다. 학습이 밤 시간대에만 돌기 때문에 30분마다 체크포인트를 저장해서, 아침에 강제로 멈춰도 다음 날 이어서 학습할 수 있게 했다.

학습 전 원본 Kanana와 Gemini로 먼저 few-shot 리포트를 만들어 기준선을 잡고, 파인튜닝 모델은 같은 입력 30개에 대한 비교에서 검증 실패율, 문체 점수, 직접 평가 점수가 모두 기준선 이상일 때만 교체한다.

### 4.6 자동매매

주문 경로는 하나뿐이다.

```
전략 (규칙) → 리스크 게이트 (규칙) → 실행기 → 증권사 API
```

**전략**

첫 전략은 단순하게 시작한다. KOSPI 상장 보통주 중 매수 이상 시그널이 나오고, 하락장이 아니고, 희석 이벤트가 없는 종목을 점수 순으로 담는다. 손절은 평균단가 대비 -7% 또는 변동성(ATR)의 2배 중 먼저 닿는 쪽, 익절은 +15% 이후 고점 대비 -5% 트레일링, 시그널이 축소·매도로 바뀌면 다음 거래일에 청산한다. 이 값들은 동작을 설명하기 위한 기본값이고, 실제 값은 백테스트와 모의투자 결과를 보고 정한다.

**리스크 게이트**

1편 4.4절의 답이다. 리스크 관리는 LLM이 아니라 **번호가 붙은 15개의 하드코딩 규칙**으로 처리한다. 대표적인 것들은 다음과 같다.

| 규칙 | 내용 |
|---|---|
| R01 | 총 투자금은 설정한 운용 한도를 넘지 않는다 |
| R02 | 종목당 비중 20% 이하 |
| R06 | 당일 손실이 -2%를 넘으면 그날 신규 매수 중단 |
| R07 | 누적 낙폭이 -10%를 넘으면 매매 전체 중단 (킬 스위치) |
| R08 | 주문 가격이 현재가와 3% 이상 차이 나면 거부 |
| R09 | 관리종목, 거래정지, 투자경고 종목 매수 금지 |
| R12 | 같은 주문 ID 중복 제출 무시 |
| R15 | KOSPI 유니버스 밖 종목 매수 금지 |

중요한 설계 포인트는 **매도가 매수보다 제약이 적어야 한다**는 것이다. 킬 스위치가 켜져 있거나 일일 손실 한도에 걸렸을 때 매수는 막아야 하지만, 손절 매도까지 막으면 손실이 더 커진다. 그래서 손절 매도는 대부분의 규칙을 통과하도록 했다.

**주문 상태 관리와 킬 스위치**

주문은 생성, 게이트 승인·거부, 제출, 부분 체결, 체결, 취소, 오류의 상태를 거친다. 증권사 응답이 불분명할 때는 **절대 재주문하지 않고** 오류로 처리한 뒤 알림을 보낸다. 중복 주문이 누락된 주문보다 훨씬 위험하기 때문이다.

킬 스위치는 텔레그램 명령, 커맨드라인, 누적 낙폭 자동 발동, 연속 오류 3건으로 켜진다. 켜지면 모든 매수가 막히고 미체결 매수 주문이 취소된다.

**모의투자에서 실전으로**

한국투자증권 모의투자 계좌로 최소 20거래일을 무장애로 운영한 뒤에야 실전으로 넘어간다. 전환 조건은 다음과 같다.

- 20거래일 연속 수집·분석·주문 오류 없음
- 리스크 게이트 시나리오 테스트 전부 통과
- 장중 킬 스위치 실제 동작 확인
- 모의투자 성과와 같은 기간 백테스트 결과의 차이 분석
- 보유 종목에 증권사 자동감시주문 병행 설정

실전은 소액으로 시작해서, 성과가 백테스트와 크게 어긋나지 않을 때 4주 단위로만 증액한다. 모의투자 기간에는 모든 메시지와 리포트 맨 위에 **[모의]** 표시를 붙여, 실전 전환 후에 헷갈리지 않도록 했다.

### 4.7 장마감 보고

장마감 보고는 모든 모듈이 합쳐지는 지점이다. 거래일 하루의 흐름은 다음과 같다.

| 시각 | 작업 |
|---|---|
| 07:30 | 전날 장 마감 이후 뉴스, 해외 시장 수집 |
| 08:30 | 전날 시그널과 장전 뉴스로 당일 주문 계획 확정 |
| 09:10 ~ 15:20 | 계획 주문 분할 집행, 손절·익절 감시 (1분 주기) |
| 11:30 | 증권사 리포트 1차 수집 |
| 15:40 | 체결·잔고 확정, 미체결 주문 취소 |
| 16:00 | 일봉, 수급, 당일 공시 수집 |
| 16:10 | 뉴스 분류 → 투자 분석 |
| 16:25 | 장마감 리포트 생성 |
| 16:30 | 텔레그램 발송 |
| 17:00 | 증권사 리포트 2차 수집 |
| 17:00 ~ | GPU 학습 시간대 |

리포트는 헤드라인, 계좌 현황, 시장, 주요 뉴스, 오늘의 리서치, 기술적 분석, 종목 분석, 내일 체크포인트 순서로 구성된다. 텔레그램에는 헤드라인과 계좌 요약, 핵심 3줄만 먼저 보내고, 전체 리포트는 HTML 파일로 첨부한다. 휴대폰 첫 화면에서 스크롤 없이 오늘의 손익과 핵심 사항을 확인할 수 있게 하는 것이 목표다.

앞 단계의 작업이 실패해도 리포트는 나간다. 뉴스 분류가 실패하면 뉴스 섹션에 "분석 지연"을 표시하고 공시 목록만 표로 보여주는 식으로, 섹션마다 대체 경로를 정해두었다. 반대로 매매는 분석이 실패하면 신규 진입을 멈춘다. **리포트는 실패해도 열리는 쪽으로, 매매는 실패하면 닫히는 쪽으로** 설계한 것이다.

리포트 디자인은 한국 시장 관례대로 상승은 빨강, 하락은 파랑을 쓰되, 색각 이상이나 흑백 환경을 고려해 항상 ▲▼ 기호와 부호를 함께 표시한다. 종목별 시그널이 어제에서 오늘로 어떻게 움직였는지를 한 줄로 보여주는 "시그널 사다리"를 리포트의 핵심 시각 요소로 정했다.

## 5. 문서화와 개발 계획

### 5.1 명세서부터 쓴다

모듈이 여러 개이고 병렬로 개발하기 때문에, 코드보다 문서를 먼저 확정했다. 작성한 문서는 다음과 같다.

| 문서 | 내용 |
|---|---|
| 개발기획서 | 목표, 지표, 로드맵, 리스크, 결정 기록 |
| 시스템 아키텍처 | 구조, 일일 스케줄, 운영 환경 |
| 데이터 명세서 | 데이터 소스, 테이블 정의, 미래 데이터 규칙 |
| 인터페이스 명세서 | 모듈 간 JSON 스키마, 슬롯 문법 |
| 모듈 명세서 (5종) | 뉴스 AI, 투자 분석 AI, 리포트 AI, 자동매매, 장마감 보고 |
| 디자인 명세서 | 색상·글꼴 토큰, 컴포넌트, 화면 구성 |
| 테스트 명세서 | 필수 시나리오, 운영 인수 기준 |
| WBS | 작업 단위 분해, 담당, 선행 작업, 완료 조건 |

개발은 Claude Code와 함께 진행할 예정이라, 저장소 루트와 모듈별 폴더에 `CLAUDE.md`를 두어 절대 규칙(LLM은 주문하지 않는다, 숫자는 슬롯으로, 미래 데이터 금지 등)과 코딩 규칙을 명시했다. 명세가 바뀌면 코드보다 문서를 먼저 고치고, 모듈 사이의 데이터 형식을 바꿀 때는 버전을 올린다.

### 5.2 로드맵

| 단계 | 기간 | 내용 | 완료 기준 |
|---|---|---|---|
| 0. 기반 | 2~3주 | 데스크탑 서버 설정, 데이터 레이어, 스키마, 수집기 | 과거 데이터 적재, 7일 무장애 자동 수집 |
| 1. 병렬 개발 | 6~8주 | 뉴스 AI, 투자 분석 AI, 리포트 데이터셋, 리서치 수집 | 각 모듈이 스키마대로 출력, 분석 백테스트 |
| 2. 통합 | 2~4주 | 매매 없는 장마감 보고 | 10거래일 연속 발송, 숫자 오류 0 |
| 3. 자동매매 | 4~8주 | 전략, 리스크 게이트, 모의투자 | 모의투자 20거래일 무장애 |
| 4. 고도화 | 이후 | 파인튜닝 모델 교체, ML 분석 모델, 소액 실전 | 실전 전환 체크리스트 충족 |

2단계에서 **매매 없이 장마감 보고부터 완성하는 것**이 중요하다. 세 모듈이 실제로 맞물리는지 돈을 걸기 전에 확인할 수 있고, 3단계에서는 계좌 현황만 추가하면 된다.

증권사 리포트 수집기는 1단계 초반에 가장 먼저 붙일 계획이다. 수집을 시작한 날부터 학습 데이터가 쌓이기 때문에, 일찍 시작할수록 파인튜닝 시점에 데이터가 충분해진다.

### 5.3 아직 정하지 않은 것

- 자동매매 운용 한도 금액 (실전 전환 전까지 결정)
- 데스크탑 운영체제 (Ubuntu 네이티브 또는 Windows + WSL2)

## 6. 다음 편에서

설계는 여기까지다. 1편에서 논문 하나로 시작한 구상이, 운영 환경과 원칙을 정하고 나니 꽤 다른 모습이 됐다. 에이전트들이 토론하는 구조에서, 계산은 코드가 하고 해석과 글쓰기는 LLM이 하고 최종 관문은 규칙이 지키는 구조로 바뀌었다.
